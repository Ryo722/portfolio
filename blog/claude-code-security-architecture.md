# Claude Codeに多層のセキュリティを設計した話

## きっかけ

Claude Codeと開発していて、ある日ふと怖くなった。

AIはファイルを読める。コマンドを実行できる。ネットワーク通信もできる。バージョン管理も操作できる。つまり、秘密情報にアクセスして外部に送る能力を持っている。

もちろんClaude Code自体に承認UIはある。操作のたびに「許可しますか？」と聞いてくれる。最初はちゃんと確認していた。だが開発に集中していると「はい」を反射的に押してしまう。ある時、自分が中身を確認せずに承認を連打していることに気づいた。

承認UIは「人間の注意力」に依存する仕組みだ。注意力は有限のリソースで、集中しているときほど枯渇する。ここに頼り続けるのは危険だと感じた。

必要だったのは、自分が注意していなくても安全が保たれる仕組みだった。

## 「自分を信用しない」という出発点

Claude Codeと相談しながら、設計の方針を固めた。

まず、許可されていない操作は全て拒否する（deny-by-default）。何か異常があれば安全側に倒す（fail-closed）。そして1つの防御が破られても次が止める（defense-in-depth）。

中でも一番こだわったのは、人間が何をしても自動的に安全が保たれるfool-proofの考え方だった。「チェックリストを毎回確認する」のではなく、「仕組みが勝手に守る」。自分の注意力を信用しない設計だ。

## 多層防御の全体像

脅威モデルから逆算して、防御レイヤーを設計した。

```
ファイルシステム権限   — OSレベルで秘密ファイルを保護
AIポリシー            — AIの行動指針をプロンプトで定義
権限拒否ルール        — 危険な操作をランタイムでブロック
ツール実行前フック     — 秘密パターンを実行前に検出・拒否
サプライチェーン対策   — 外部依存のバージョン固定と定期監査
Gitフック             — commit/push時の秘密スキャンと保護
事後監査・記録        — コマンドログと自動リダクション
秘密管理             — OSレベルの秘密ストアと環境分離
環境分離             — 作業ディレクトリと秘密保管の物理分離
定期監査自動化        — ログローテーションと定期監査
オンデマンド監査      — 複数の専門エージェントによる並列監査
```

最初からこの形だったわけではない。後述するが、段階的に育てた結果こうなった。

### 脅威をどう考えたか

秘密が漏洩する経路を洗い出した。

主な脅威は、秘密ファイルへの直接的なアクセス、別の実行経路を経由した間接的なアクセス、そして取得した秘密の外部への送出だ。

それぞれに対して複数の層が重なって防御する。1つの層が突破されても、次の層が止める。これがdefense-in-depthの考え方だ。

層の役割は「予防」「検出」「記録」「監査」の4フェーズに分かれる。予防が最も厚い。「検出して通知する」より「そもそも実行させない」方が安全だからだ。

## つまずいたこと・学んだこと

### ルール数が想像以上に膨れた

「危険なコマンドだけブロックすれば十分」と最初は思っていた。

甘かった。脅威モデルを書き出すと、秘密情報を含みうるファイルは多岐にわたる。しかも同じファイルに対して、複数のアクセス経路それぞれに拒否ルールが要る。アクセス手段が違えばルールの書き方も違うからだ。

結果として想像以上の数になった。「少なくしたい」という気持ちと「漏れがあったら終わり」という恐怖の間で、脅威モデル側を優先した。

### fail-closedは最初つらかった

全てのフックを「異常があれば拒否する」設計にした。

```
何らかの異常が発生  → 拒否
検査に不合格       → 拒否
全ての検査に合格    → 許可（唯一の許可パス）
```

導入直後、誤検知で正当な操作がブロックされることがあった。正直ストレスだった。

だが、誤検知で作業が止まるコストと、秘密が漏洩するコストは比較にならない。誤検知は「安全側の失敗」だ。そう割り切ってからは気にならなくなった。フックの精度は使いながら改善していけばいい。

### 秘密をファイルに残さない選択

秘密管理にはいくつかの方法がある。設定ファイルに直書き、環境変数と外部ディレクトリ参照、OSレベルの秘密ストア。

高リスクなプロジェクトではOSレベルの秘密ストアを採用した。秘密がファイルシステム上に永続化されないので、AIのファイルアクセスやGit操作による漏洩リスクを原理的に排除できる。

設定は複雑になるが、「ファイルに秘密が存在しない」という状態は強力だ。漏れようがない。

開発系プロジェクトでは、環境変数の自動注入と外部ディレクトリ参照を組み合わせている。リスクレベルに応じて使い分けることで、利便性と安全のバランスを取った。

## 自動化で自分を信用しない

セキュリティは設計して終わりではない。維持し続ける仕組みが要る。

### セッション開始時の自動検証

開発セッションが始まるたびに、セキュリティインフラの状態を自動チェックする仕組みを入れた。作業環境の制約、秘密スキャンツールの存在、秘密管理の状態。毎回勝手に確認される。

「チェックリストを毎朝見る」みたいな運用は、自分の性格上3日で破綻する。仕組みに任せた。

### 定期的な自動監査

監査ログのローテーションと、外部依存の監査を定期的に自動実行している。人間の介入は不要。忘れても、休んでいても、安全は維持される。

### 並列エージェント監査

PR作成前や大きな変更の後には、複数の専門エージェントが並列で監査を実行する。秘密の混入、脆弱性パターン、依存関係のリスクなど、複数の観点から同時にチェックする。

これはClaude Codeのマルチエージェント機能を活かした設計で、直列だと時間がかかる監査を並列で回せる。AIと一緒にセキュリティを回す、という感覚に近い。

## 限界を認識しておく

この設計は万能ではない。

自動検出には原理的な限界がある。複数の検出手法を重ねて補完しているが、あらゆるケースに対応できるわけではない。

この設計の主目的は、日常の開発作業における秘密漏洩事故の自動防止だ。多層防御により迂回も困難にしているが、全ての攻撃シナリオを想定したものではない。

多数のルールとフックの設定・保守にはコストがかかる。全ての開発者に推奨する規模ではなく、秘密を扱うプロジェクトの数と性質に応じた判断だ。

限界を知った上で使う。そのスタンスが重要だと思っている。

## 振り返り

### 育てたセキュリティ

最初から多層を設計したわけではない。

最初はファイル権限を制限しただけだった。次に拒否ルールを手動で追加した。フックでパターン検出を加え、定期監査を自動化し、段階的に層を増やした。

[AIと回す運営OS](/portfolio/blog/multi-agent-orchestration.md)でも同じことを書いたが、**運用 → ルール化 → 自動化**の順序が大事だ。いきなり自動化すると、何を自動化すべきかがわからない。まず手動で痛みを感じてから仕組みにする。

セキュリティも同じだった。最初の「怖い」という感覚がなかったら、ここまで層を重ねなかったと思う。

### 「何が危険か」を考え続ける

脅威モデルを書く作業は、そのまま「何を許可すべきか」の判断基準になった。

曖昧な許可を排除し、明示的な許可だけを残す。この考え方はセキュリティに限らず、API設計やデータフロー設計にも使えると感じている。

AI Coding Assistantのセキュリティは、まだ確立されたプラクティスが少ない領域だ。この設計が正解かはわからない。ただ、「自分の注意力を信用しない」という原則は、AIと一緒に開発する上でこれからも大事になると考えている。
