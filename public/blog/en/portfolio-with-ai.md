# Building a portfolio with AI — the entire process

## What I did

This portfolio site itself was built through co-development with Claude Code. From research to design, implementation, deployment, and even OS-ification of site operations. Within a single session, the following steps were completed in order:

1. Full inventory of local repositories (26 projects)
2. Scoring and candidate selection
3. Tech stack selection with codex review
4. MVP implementation (Vite + React + TypeScript + Tailwind CSS 4)
5. GitHub Pages deployment
6. Design improvements
7. Screenshots, OGP, Lighthouse optimization
8. English support + dark mode + Analytics
9. Portfolio OS construction (5-gate quality model)
10. Blog production OS (agents + skills + workflows)
11. Blog article writing, security review, and publication

## Research phase — 26 projects classified in minutes

The first step was surveying all directories under Documents.

Using `.git` presence, `package.json` or `requirements.txt` existence, and `src/` directory detection, 26 project candidates were automatically extracted.

Then each project's README, package.json, git log, and source code were investigated by parallel agents. AI ran 4-5 investigation agents simultaneously, collecting overviews of all projects in minutes.

This would take half a day if a human checked one by one.

## Scoring — technical depth × originality × completeness

Each project was rated on 5 axes (technical depth, originality, completeness, continuity, portfolio fitness) on a 1-5 scale and classified into Tier S/A/B/C.

The biggest discovery was **DuelMasters Plays**. 386 commits, 152 modules, 1,565 tests, 11,000+ card definitions. Even I was surprised: "It had grown to this scale." AI objectively tallied the numbers, making the project's true scope visible.

## Design phase — codex review

For tech stack selection, we compared Vite + React vs Next.js, choosing Vite for GitHub Pages compatibility.

This plan was submitted for review to codex (OpenAI Codex CLI). The feedback was precise:

- Tailwind CSS 4 breaks if mixed with v3 config → unify with `@tailwindcss/vite`
- ProjectDetail: accordion is more cost-effective than modal
- Deploy via GitHub Actions has better reproducibility than `gh-pages` package
- Data structures should be multilingual-ready from the start

An AI-to-AI review system (Claude Code + codex). The human only reads feedback and decides what to adopt.

## Implementation — start from type definitions

Implementation began with data layer type definitions.

```typescript
type LocalizedText = {
  ja: string
  en?: string
}
```

Defining this `LocalizedText` type first meant that adding English later required no full rewrite. The codex suggestion to "make it multilingual-ready from the start" paid off.

## Deploy — 30 seconds from push to live

GitHub Actions triggers build and deploy on push to main. About 30 seconds from push to production.

This CI/CD pipeline was also generated by AI. The human just verifies it works.

## OS-ification — 5-gate quality model

After the site was running, we systematized quality management. Design patterns proven in NanyaKanya (novel production OS) and KomoriAmado (VTuber agency OS) were applied to the portfolio.

Five gates must be passed before publishing:

| Gate | Content | Method |
|---|---|---|
| Security | No secrets or local paths | Auto |
| Performance | Build success, bundle size in range | Auto |
| Accessibility | Motion preference, keyboard accessible | Auto |
| Brand | Tone consistency, technical accuracy | Auto |
| Deploy Readiness | All gates confirmed | Human required |

Plus, 10 skills and 8 commands were defined. `/add-project` adds projects, `/deploy` runs gate checks + deployment, `/write-blog` runs the full blog production pipeline.

## Blog production OS — articles also co-created with AI

The blog article production pipeline was also OS-ified.

```
[Plan] blog-planner → Human approval
  ↓
[Write] blog-writer (+ blog-voice)
  ↓
[Review (3-parallel)]
  blog-reviewer ∥ brand-guard ∥ blog-security-reviewer
  ↓
[Publish] blog-publisher → 5 gates → Human final approval
```

The `blog-voice` skill defines tone, and `blog-security-reviewer` checks for infrastructure information exposure. In fact, the home server article nearly published SSH usernames and UFW rule specifics, which the security review caught and fixed.

## What the human did vs. what AI did

Looking back at the entire process, the human-AI role division was clear.

**What the human did:**
- Deciding which projects to include ("this goes in, this doesn't")
- Adjusting self-introduction nuance ("built solo" → "built with AI")
- Final design decisions (color, layout, font preferences)
- Security policy decisions (what to publish, what to redact)
- Blog topic selection and prioritization

**What AI did:**
- Auto-surveying, classifying, and scoring 26 projects
- Implementing components, styling, and data structures
- Generating GitHub Actions workflows
- Designing and implementing the 5-gate quality model, skills, and commands
- Blog material collection, writing, and security review

## Reflections

**AI is overwhelmingly fast at research and implementation.** Surveying 26 projects, generating components, designing workflows — these take days manually. AI does them in minutes to tens of minutes.

**Humans can focus on judgment and direction.** "What to include," "how to present it," "what to publish and what to redact" — these judgments are uniquely human. Because AI handles preparation, humans can focus solely on decisions.

**OS-ification sustains quality.** It's not just about building a site. The 5-gate quality model and skill/command system ensure the same quality standards are maintained for future updates. This very blog article went through blog-security-reviewer before publication.
