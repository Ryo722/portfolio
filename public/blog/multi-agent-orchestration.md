# Claude Codeで「AIと回す運営OS」を3ドメインに展開した

## 3つの運営OS

個人で3つの異なるドメインの運営OSを、Claude Codeのエージェント・スキル体系で構築・運用している。

| OS | ドメイン | エージェント | スキル | コマンド |
|---|---|---|---|---|
| NanyaKanya | 小説出版社 | 8 | 40 | 15 |
| KomoriAmado | VTuber事務所 | 11 | 13 | 14 |
| ryu-ailab-business | SNS収益化 | 0（スキル中心） | 11 | 0（takt自動化） |

「運営OS」と呼んでいるのは、企画→制作→審査→公開→分析という業務フロー全体を、1つのリポジトリ内でエージェントとスキルが回す仕組みだからだ。人間は方針を決めて最終承認するだけ。それ以外の実務は、AIが自律的に実行する。

## なぜ「OS化」するのか

きっかけは単純で、1人で3ドメインを回すのが物理的に無理だったからだ。

小説を書きながら、VTuberの配信企画を立て、SNSの投稿スケジュールを管理する。それぞれに品質基準があり、権利確認があり、公開前チェックがある。手作業で回すと、どこかで必ず抜け漏れが出る。

そこで、各ドメインの業務をエージェント（意思決定）とスキル（実務）に分解し、定型業務は自動実行、判断が必要な部分だけ人間に上げる——という仕組みを作った。

## エージェントとスキルの設計原則

3つのOSに共通する設計原則がある。

**エージェントは意思決定だけ。実務はスキルに委任する。**

NanyaKanyaの場合、studio-ceo（エージェント）が「次に何をすべきか」を判断し、nk-prose-writer（スキル）やnk-reviewer（スキル）に具体的な作業を委任する。エージェントは判断する。スキルは手を動かす。この分離が明確だから、役割の入れ替えや追加が容易になる。

**スキルは3層構造。**

```
skills/
└── nk-prose-writer/
    ├── SKILL.md         # エントリーポイント（何をどう実行するか）
    ├── references/      # 参照資料（判定基準、ガイドライン）
    └── examples/        # 具体例（OK/NG例）
```

SKILL.mdが手順書、referencesが判断基準、examplesが具体例。この3層があれば、AIは一貫した品質で作業を実行できる。

**ドメインが違っても構造は同じ。**

小説もVTuberもSNSも、業務の構造は「企画→制作→審査→公開」だ。違うのは各ステップの中身だけ。だから、OS自体の骨格（エージェント/スキル/ゲート/コマンド）は共通で、ドメイン固有のスキル内容だけを差し替える。

## 5ゲート品質モデル

3つのOSに共通で導入しているのが、5段階の品質ゲートだ。

```
1. Brand Gate       — ブランド整合性（自動）
2. T&S Gate         — 安全性確認（自動 + 人間判断）
3. Rights Gate      — 権利・法務確認（自動 + 人間判断）
4. QC Gate          — 品質検品（自動）
5. Publish Gate     — 最終公開承認（人間必須）
```

「風上（制作段階）で品質を作り込む」のではなく、「風下（公開前）でゲートを通す」設計にしている。制作段階ではAIに自由に書かせ、公開前のゲートで基準を満たしているか検証する。

NanyaKanyaでは、小説の各章がこの5ゲートを全て通過しないと公開できない。Brand Gateでは禁止表現をチェックし、T&S Gateではトリガー警告の要否を判定し、Rights Gateでは著作権を確認する。

KomoriAmadoでは、配信・動画コンテンツに対して同じ5ゲートが適用される。特に音声・映像の権利確認（`audio-visual-rights-check`）は、BGM・SE・ゲーム映像の使用許諾を自動チェックする。

## 3つのOSの個性

骨格は共通だが、各OSには明確な個性がある。

### NanyaKanya — 40スキルの創作特化型

小説出版社OSとして最も成熟している。98コミットで継続的に改善されてきた。

特徴的なのは創作に特化したスキル群だ。`nk-prose-writer`（執筆）、`nk-dialogue`（会話文）、`nk-character-design`（キャラクター設計）、`nk-metaphor-system`（メタファー体系設計）など、小説制作の各工程に専門スキルがある。

さらに品質面では、`nk-interest`（面白さ診断）というスキルが面白い。予測とのずれ・身体性・変化の知覚という3要素で原稿を分析し、「体験密度」を高める改善案を出す。品質を「正しいか」だけでなく「面白いか」で測る仕組みだ。

### KomoriAmado — 11エージェントの組織型

VTuber事務所OSとして、最も多くのエージェント（11人）を持つ。Chief of Staff、Talent Manager、Content Strategist、Legal & Rights Officer——リアルな事務所組織をそのままエージェント化した。

特徴的なのは安全運営への注力だ。Trust & Safety Officer（エージェント）が常にモデレーション判断を担い、`brand-guard`スキルが全コンテンツのトーンを自動検証する。VTuber活動はリアルタイム性が高く、一度公開したものの取り消しが難しい。だから公開前の安全確認に最も手厚い設計になっている。

### ryu-ailab-business — taktで完全自動化

SNS収益化OSは、3つの中で最も自動化度が高い。エージェントを置かず、11個のスキルとtakt（マルチエージェントオーケストレーションエンジン）の4ワークフローで全業務を回す。

```
/ceo "今週のnote記事を企画して"
  → 指示分析 → タスク分解 → 並列委任（researcher + note-manager）
  → レビュー → 統合 → ログ記録
```

CEOスキルに指示を出すだけで、分析・委任・実行・レビュー・統合・記録が全自動で走る。人間は最終確認のみ。30日でMVPを作るという制約の中で、「人間の判断回数を最小化する」ことに振り切った設計だ。

## 自動化は段階的に深化する

3つのOSを見比べると、自動化度が段階的に深化していることがわかる。

```
NanyaKanya（2026-01〜）:  手動コマンド中心     自動化 40%
KomoriAmado（2026-03〜）: エージェント判断型    自動化 60%
ryu-ailab（2026-03〜）:   takt完全自動化        自動化 90%
```

これは意図的な設計だ。

NanyaKanyaは最初に手動でワークフローを回し、「何が定型で、何が判断を要するか」を実運用で見極めた。その知見をKomoriAmadoにフィードバックし、エージェントの判断範囲を拡大した。ryu-ailab-businessでは、前2つの知見を全て注入して最初からtakt自動化に振り切った。

**運用実績 → ルール化 → 自動化**。この順序を守ることで、「自動化したけど意図と違う動きをする」という事故を防いでいる。

## セキュリティは「できないようにする」

3つのOSに共通するセキュリティ方針がある。

「承認UIで毎回確認する」のではなく、「危険操作を実行不能にする」。

具体的には、OS/shell wrapperで破壊的コマンド（rm -rf, git push --force等）をブロックし、Git hooksでprotected branchへの直接pushを防止する。Claude自身は「危険だと判断したら実行しない」設計になっている。

これは「人間に聞く」より「そもそもできない」方が安全だという考えに基づく。判断疲れがない。人間が寝ていても安全に回る。

## 振り返り

3つの異なるドメインで運営OSを作ってみて、見えてきたことがある。

**OSの骨格は使い回せる**。エージェント/スキル/ゲート/コマンドという4要素の構造は、ドメインに依存しない。小説でもVTuberでもSNSでも、同じ骨格の上にドメイン固有のスキルを載せるだけで機能する。

**自動化の前に手動運用**。いきなり自動化すると、何を自動化すべきかがわからない。まず手動で回し、定型業務と判断業務を見極め、定型だけを自動化する。この順序が品質を守る。

**1人 × AI = 小さな組織**。8エージェント、40スキル——これは1人で運用している。AIが実務を担い、人間が方針を決める。この分担が明確なら、1人でも組織的な品質管理が成立する。

次のステップとして、3つのOSで蓄積した設計パターンを抽象化し、新しいドメインへの展開をさらに容易にしたい。実際、このポートフォリオサイト自体を4つ目のOSとして構築している。
