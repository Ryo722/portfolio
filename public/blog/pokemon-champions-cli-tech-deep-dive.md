# ポケモンチャンピオンズCLIの裏側 — `@smogon/calc`差分・Nash均衡選出・27 Sprint不変な`0.0574881158647651`の設計

前作 [「勝てるパーティを自動で出すツール」を作ってみたら、勝率5割で寝かせることにした話](./pokemon-champions-cli-tried-but-fell-short.md) で書いたツールは、表側だけ見ると勝率5割の失敗談だ。

裏側はそれなりに作り込んである。CLI 21本、テスト 3,380件、Sprint 63.5まで Claude と一緒に積み上げた。`0.0574881158647651` という IEEE 754 exact double を **27連続 Sprint で1bitも動かさない**運用を回している。

この記事はその裏側の話だ。同時に、**技術的な精度ばかり詰めて、実戦での有効性検証を後回しにし続けた反省**の記録でもある。AIと一緒に開発するときに、自分が踏んだ罠の話と言ってもいい。

## 全体を5層で押さえる

このツールは大きく5層に分かれている。

```
[データ層]    season/regulation JSON（使用率・レギュレーション）
     ↓
[計算層]      @smogon/calc + チャンピオンズ固有 override
     ↓
[構築層]      exhaustive / GA optimizer + 4指標 evaluator
     ↓
[選出層]      lineup-nash（C(6,3)=20通り、20×20 payoff Nash均衡）
     ↓
[戦績層]      session log/stats/insight + meta-divergence
```

CLI は21本あるが、機能カテゴリで圧縮すると5つに収まる。構築・対戦シム / 情報参照 / 統計ビュー / AP配分 / box・戦績・データ。各 CLI は計算層と構築層を共有し、用途別に薄いラッパを被せている。

依存ライブラリは `@smogon/calc` (MIT) / `commander` (MIT) / `zod` (MIT) / TypeScript (Apache-2.0) / `vitest` (MIT)。GPL系は意図的に避けた。OSSとして配布する前提で組んでいるからだ。

## `@smogon/calc` の上にチャンピオンズ固有差分を被せる

ポケモンチャンピオンズはルールが本家とずれている。

- レベルは Lv50 固定
- 個体値は全部 31 固定
- 努力値の代わりに **能力ポイント（AP）66pt を6ステータスに配分**（各 stat ≤ 32pt）
- メガ進化 + テラスタル + ギガンタマックスが**同時に存在する**

`@smogon/calc` をforkして本体に手を入れる選択肢もあった。やめた理由は、依存更新を切らないためだ。本家が新世代対応や種族値修正を出したら、それを取り込み続けたい。forkすると、merge負債が雪だるま式に増える。

なので **override 方式**にした。`src/calc/species-overrides.ts` がチャンピオンズ固有のメガ種族値・タイプ差分を保持し、`resolveSpeciesBaseStats(name, gen)` で canonical な `@smogon/calc` 値の上に差分を重ね書きする。`@smogon/calc` 本体は触らない。

overrideによる修正の代表例は、Sprint 54.5 で「Aegislash の実数値が観測と合わない」と判明したケースだ。調査の結果 **`@smogon/calc` 本体は本家 Gen6+ 準拠で正確だった**と分かったことだ。攻撃、特攻の種族値を現在の140に修正したところ、`floor((140 + 20 + 32) × 1.1) = 211` という単純な計算で観測値と一致した。


## 評価関数の4指標と、「土台が甘い」自覚

パーティ評価は4指標の重み付き和で出している。エース性 0.4 / 補完 0.25 / 壁 0.15 / タイプ一貫性 0.2。各指標は「上位30匹の各相手に対して、自軍6匹のうち最低1匹がA以上の有利を取れているか」を集計する。

カバー率 93% という数字はここから出る。30匹の相手のうち約28匹に、何らかの形で有利が取れているということだ。

数字としては嘘ではない。検算は何度もしたし、テストも 3,380 件通っている。

ただ**根本的な弱点**がある。これは正直に書いておきたい。

**4指標のいずれも、評価の最小単位は「1体対1体」のマッチアップ**だ。それを6匹分積み上げてカバー率にしている。**実戦で起きる「6対6のうち3対3を選出して、行動順と役割分担で勝負が決まる」という組合せ戦は、評価関数のレベルではモデル化できていない**。

前作で書いた「勝率5割」の根本原因は、つきつめるとここに行き着く。土台で測っているものが、実戦で問われているものとずれている。

## Nash均衡選出（`lineup-nash`）— きれいな上物、甘い土台

組合せ戦の問題には別レイヤーで一応手を打った。`lineup-nash` コマンドだ。

ロジックは単純で、自軍6匹から3匹選ぶ組合せは C(6,3) = 20通り、相手も同じく20通り。**20 × 20 の payoff 行列**を作って、各セルに「自軍のこの3匹で、相手のこの3匹を相手にしたときの期待勝率」を埋める。これを混合戦略 Nash 均衡で解いて、自分の選出を最適化する。

ゲーム理論の教科書に書いてある話そのままなので、実装は素直に書ける。pkdx (MIT) の `payoff_semantics.md` から定式の参照だけ拝借して、コードは独立に書いた（直接コピー禁止、`Adapted from` ヘッダで明示）。

問題は **20×20 の各セルに埋まる「期待勝率」の精度**の方だ。

各セルの期待勝率は、内部的には `screened-mc`（screened Monte Carlo）と DP 系の depth-limited minimax で算出している。ところが、その元になっているマッチアップ判定そのものが、前章で書いた通り「1体対1体」評価の積み上げでしかない。

つまり**土台が甘いまま、その上にきれいなゲーム理論を載せても、出てくる答えは土台の甘さを引きずる**。Nash均衡を解くこと自体は数学的に正しい。でも入力が甘ければ、解も甘い。GIGO は機械学習に限った話ではない。

これが前作で「複合情報のモデル化が一番根が深い」と書いた中身だ。きれいな上物を載せても、土台に手を入れない限り報われない、という構造になっている。

## 開発運用 — Sprint標準8ステップ + Codex 2段階レビュー

個人開発でここまで運用に振った理由は1つで、**自分の判断を1人で擁護したくなかった**からだ。

Sprint 標準 8 ステップは以下のように回している。

1. handoff doc 作成（前 Sprint result から引継ぎ）
2. 投入前チェック 4 項目（`npm test` / `tsc` / `git status` / 前 Sprint result 確認）
3. plan-input v1 起草（諮問事項 Q1-Qn を含む）
4. **Codex 計画レビュー**（厳格判定）
5. 確定版 plan（採択結果反映）
6. 実装（TDD + Codex 採択 + 不変堅持 9 項目を毎ステップ確認）
7. diff-input 起草 → **Codex 差分レビュー**
8. fix + result + memory + クローズ commit

Codex は GPT-5/Opus 系の外部レビュア役で、計画段階と差分段階の2回 諮問する。Sprint 41 から 63.5 通算で **27/27 GO 相当**を達成している（うち純 GO 7回、CONDITIONAL GO は即時反映で純 GO 相当に昇格させる運用）。

当然ながら、Codex に NO-GO を食らった回ほど、**自分が見えていなかった前提**が出てきた。Sprint 58 で `stateKey()` の opaque packed string 化を計画したら、`tests/battle/state-key.test.ts` が `toContain("tc=3")` で format を直接検証している、と指摘されて引き戻された。tests を snapshot 更新だけでは済まない、と。

これは Claude と2人で見落としていた。Claude は試作も実装も速いが、**「既存テストが何を保証しているかの読み込み」と「自分の計画がそれを破るかの照合」**は、自分が手を抜くと一緒に抜ける。Codex を入れた一番の効用はそこだった。

## 振り返り — Claudeに任せて作りすぎた反省

ここまで書いてきた技術的精度は、**Claude と一緒だから到達できた**ものだ。1人だったら 21 CLI も 3,380 テストも、27 Sprint の不変堅持も、たぶん作れていない。少なくとも作れていてもこの速度ではなかった。

ただ、それと裏腹に、**いちばん大事なことを後回しにし続けた**自覚がある。

Sprint が回るたびに `npm test` が緑になり、Codex が GO を出し、deterministic value が動かない。指標は全部良い方向に伸びる。**「これだけ品質を積めば、実戦でも勝てるはず」**と無意識に思い込んでいた。

実戦に持ち込んだのは、ツールが実用最低ラインに達してからかなり後だった。30戦弱で勝率5割と分かったとき、もっと早く持ち込んでおけばよかったと素直に思った。「精度の出ているツール」を作っているつもりで、実は**「精度の指標が動くツール」**を作っていた。両者は別物だ。

Claude と一緒に開発するときの罠は、たぶんここにある。

- スピードが出る分、**「動いているか」「テストが通るか」「レビュアが GO を出すか」が、本来の価値検証より先に揃ってしまう**
- 揃った瞬間に「進んでいる」と感じてしまい、**「これは実戦で効いているか」を問う頻度が下がる**
- 結果、**技術的精度だけが先に走る**

Sprint 標準 8 ステップに「実戦投入したか / 何戦したか / 勝率はどうか」を不変項目として入れていれば、もっと早く軌道修正できた。次に AI と一緒に何かを作るときは、**最初の Sprint から「効いているか」を測る項目を埋め込んでおく**つもりだ。

## おわりに

このツールの裏側は、技術的にはきれいに作れている部分もある。`@smogon/calc` 上の override 方式、20×20 payoff 行列の Nash 均衡、8層の多重防御など。1つずつは、書いていて楽しかった。

ただ全体としては、**「鉛筆をきれいに削り続けて、文字を書くのを忘れていた」**みたいな状態だった、というのがいまの自分の評価だ。

Claude と一緒に開発するスタイルからはもう逃れられない。だからこそ、Claude をフル活用しつつも**「効いているか」だけは別レイヤーで測り続ける**仕組みを、次のプロジェクトには最初から埋めておきたい。

このツール自体は、前作で書いた通り、しばらく寝かせる。寝かせている間に、評価関数の土台側を組み直すアイデアが固まってきたら、また再開、再構築する予定。
