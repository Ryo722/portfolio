# 11,000枚のカードを動かすゲームエンジンをAIと書いた話

> **注**: 本記事の数値（テスト数・コミット数等）は2026年3月時点のものです。最新の数値はプロジェクトページをご覧ください。

## 何を作ったか

デュエル・マスターズのオンライン対戦プラットフォーム「DuelMasters Plays」を個人で開発している。AI対戦（オフライン）とSocket.IOによるリアルタイムオンライン対戦の両方に対応したフルスタックアプリケーションだ。

規模感を先に示しておく。

| 指標 | 数値 |
|---|---|
| コミット数 | 374 |
| エンジンモジュール | 152ファイル |
| エンジンコード | 32,776 LOC |
| テストケース | 1,065+ |
| カード定義 | 586,677行（11,000枚超） |
| コマンド種別 | 35種 |

技術スタックはNext.js 14 + TypeScript + Express + Socket.IO + Prisma + PostgreSQL。フロントエンドからバックエンド、DB、Docker、CI/CD、自宅サーバーデプロイまで、AIと一緒にフルスタックで構築している。

このうち最も設計に時間をかけたのが、ゲームの心臓部であるルールエンジンだ。

## なぜ純粋関数型にしたか

エンジン全体の設計は「1つの関数に全てを集約する」というシンプルな原則に基づいている。

```typescript
function processCommand(
  state: GameState,
  playerId: PlayerId,
  command: GameCommand,
  cardCatalog: Map<string, CardDef>
): CommandResult
```

`processCommand()` がエンジンの唯一のエントリポイントだ。現在のゲーム状態、プレイヤーID、コマンド、カード定義を受け取り、新しい状態とイベントを返す。副作用はない。

この設計にした理由は3つある。

**テスタビリティ**。純粋関数なので、入力を与えれば常に同じ出力が返る。テストが書きやすく、1,065件のテストケースが自然に積み上がった。

**リプレイ可能性**。コマンド列を記録しておけば、そのまま再生できる。SeededRNGと組み合わせることで、AI対戦も含めて完全に決定論的なリプレイが可能になった。

**フロント・バック共有**。エンジンはフロントエンドでもバックエンドでも動く。オフラインAI対戦ではクライアント側で直接実行し、オンライン対戦ではサーバー側で実行する。同じコードが両方で動くのは、副作用がないからこそ成立する。

内部は35種のコマンドに対するswitch分岐で構成されている。

- プレイコマンド（10種）: CHARGE_MANA, SUMMON_CREATURE, CAST_SPELL ...
- 戦闘コマンド（1種）: ATTACK
- 能力コマンド（1種）: ACTIVATE_ABILITY
- フェーズコマンド（3種）: ADVANCE_PHASE, END_TURN, SURRENDER
- 選択コマンド（3種）: CHOOSE_CARDS, CHOOSE_YES_NO, CHOOSE_OPTION
- フリーモード用（15種）: MANUAL_MOVE_CARD, MANUAL_TAP ...

各コマンドの処理後に `applyPostActionSBA()`（状況起因処理）が走り、ルールに基づく自動処理が適用される。

## 11,000枚のカードをどう扱ったか

デュエル・マスターズには11,000枚を超えるカードがある。それぞれが固有の能力を持ち、組み合わせで無数のインタラクションが生まれる。

カード定義は公式データのJSONから、6種のビルダーで型安全なCardDef型に自動変換している。

| ビルダー | 対象 |
|---|---|
| normalCardBuilder | 通常クリーチャー・呪文・多色カード |
| psychicCardBuilder | 2面/3面サイキック（覚醒ステージ対応） |
| dragheartCardBuilder | ドラグハート（3面龍解チェーン） |
| twinpactCardBuilder | ツインパクト（スキル分割） |
| duelistCardBuilder | デュエリスト |
| auraCardBuilder | オーラ |

特に複雑なのがPsychicカード（3面覚醒）とDragheartチェーン（3面龍解）だ。1枚のカードが最大3つの面を持ち、条件に応じて変形する。これを型システムで表現するのに苦労した。

キーワード能力は12種をサブモジュール化している。忍者系（`ninjaSystem.ts`）、ドラゴン系（`dragheartSystem.ts`）、特殊系（`invasionSystem.ts`, `dynamoSystem.ts`）など、それぞれが独立したハンドラとして効果レジストリに登録される。

置換効果（総合ルール609条）は `replacementEffects.ts` で一元管理している。「破壊される代わりに」「墓地に行く代わりに」といった置換効果の優先順位解決は、カードゲームエンジンで最も厄介な部分の一つだ。

## AIとの共同開発で変わったこと

このプロジェクトはClaude Codeとの共同開発で進めている。AIとの協業で大きく変わったことが3つある。

**TDDが自然に回る**。AIにテストを先に書かせ、最小限の実装を書き、リファクタリングする——このサイクルが人間1人のときより格段に速い。テストケースが1,065件まで積み上がったのは、AIとのペアプログラミングのおかげだ。

**設計パターンの発見が早い**。循環依存の解決に `setXxxOps()` というDIパターンを導入したが、これはAIとの対話の中で自然に出てきた。人間がアーキテクチャ方針を示し、AIが具体的な実装パターンを提案し、人間がレビューして採用する。この往復が設計の質を上げている。

**4並列レビュー体制**。takt（マルチエージェントオーケストレーションエンジン）を使い、DM総合ルール専門家・キーワード能力専門家・効果処理専門家・エンジン検証専門家の4エージェントが並列でレビューする体制を構築した。1人で開発しているのに、4人分の専門的なレビューが走る。

一方で、**UIの開発は人間がドライブする必要がある**。対戦画面のレイアウト、カードのドラッグ＆ドロップの挙動、フェーズ表示の位置、シールドゾーンの見せ方——こうしたUIの設計と調整は、AIがコードを生成するだけでは完成しない。

実際に触って、「ここが使いにくい」「この情報が足りない」「この操作が直感に反する」と感じるのは人間だけだ。AIに「右クリックでコンテキストメニューを出して」と伝えることはできるが、「このメニューが出るタイミングが0.3秒遅い」という感覚はプレイヤーとして自分で触らなければわからない。

UI開発は、AIにコード生成を任せつつ、人間がトライアンドエラーでドライブするのが現時点での最適解だと感じている。AIが得意なのはロジックの実装とテスト。人間が得意なのは体験の設計と感覚的な調整。この役割分担が、AIとの共同開発で最も重要な学びだった。

## AI対戦エンジンの実装

オフラインのAI対戦は、ボード状態の数値化（スコアリング）で実装している。

```
スコア = (自軍パワー合計 - 相手パワー合計) / 1000
       + (自軍シールド数 - 相手シールド数) × 2
       + (自軍手札数 - 相手手札数) × 0.5
```

この評価関数をベースに、難易度別に戦略を分岐させている。

| 難易度 | 戦略 |
|---|---|
| EASY | ランダム選択 |
| NORMAL | 評価関数ベースの貪欲法 |
| HARD | 評価関数 + ブロッカー検出による防御評価 |

SeededRNGを統合しているため、同じシード値なら同じ局面展開になる。これによりリプレイ機能が成立し、デバッグ時にも「あの局面を再現して」が可能になった。

AI関連のコードは合計862行。小さいように見えるが、`processCommand()` の純粋関数設計のおかげで、AI側はコマンドを生成して渡すだけでよい。ゲームルールの複雑さはすべてエンジン側に閉じている。

## 振り返りと次のステップ

374コミット、32,776行のエンジンコード、1,065件のテスト。個人開発としてはかなりの規模になった。

学んだことを3つ挙げる。

**純粋関数は正義**。副作用がなければテストが書ける。テストがあればリファクタリングできる。リファクタリングできれば設計を改善し続けられる。この正のサイクルが、複雑なカードゲームのルールを安全に実装する基盤になった。

**AI共同開発は「役割分担」**。ロジックとテストはAIが速い。UIと体験設計は人間がドライブする。設計方針は人間が決め、実装パターンはAIが提案する。この分担が明確になるほど、開発速度も品質も上がる。

**11,000枚は「仕組み」で解く**。1枚1枚に個別対応するのではなく、カードビルダー × キーワード能力モジュール × 効果レジストリという仕組みで汎用的に処理する。個別のカードは定義データとして扱い、エンジンは定義を解釈する側に徹する。

次のステップとして、エンジン強化計画で6つの品質属性（決定性・拡張性・検証可能性・保守性・安全性・追跡可能性）を段階的に改善していく予定だ。既存の1,065+テストを壊さずに、内部基盤を非破壊的に進化させる——これもまた、純粋関数設計のおかげで可能になるアプローチだ。
